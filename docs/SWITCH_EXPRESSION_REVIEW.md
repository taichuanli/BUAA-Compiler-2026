## 实现要点

1. `Lexer` 为紧邻的 `->` 生成 `ARROW`；独立 `-`、`>` 保持原类别，
   注释、字符串与字符中的内容按原有词法规则处理。
2. `PrimaryExp` 新增 `SwitchExp`；`parseSwitchExp`、`parseSwitchArm` 分别
   在归约后输出 `<SwitchExp>`、`<SwitchArm>`。分支值继续复用完整 Exp。
3. Stmt 遇到 switch 仍固定进入原有语句分支，输出 CaseStmt 并使用冒号；
   不通过观察分隔符来猜测应使用哪一种 switch。
4. 缺少 `->` 报 o，定位到前一个终结符，不推进 token；i/j 复用同一恢复
   方式。下一分支的关键字或分支值的首 token 保留给后续正常分析。
5. 数组赋值的前瞻按方括号和花括号层次扫描，避免被下标里的分支分号截断；
   同时允许跨行赋值，并保留缺 `]` 的 k 恢复。
6. 字符常量输出由项目原有 `CHRCON` 调整为题面指定的 `CHARCON`。

完整编译器源码仍保留在仓库，提交包只包含本题依赖的 10 个 Java 源文件和
`config.json`；顶层 Java 文件仅有 Compiler.java，不包含 src 包装层、class、
JAR、第三方库或后端源码。

## 难度评估

**整体偏易至中等，约 2.5/5。** 对已经完成稳定递归下降前端的同学，
核心改动只是新增两个产生式、一个 token 和一种插入式错误恢复；无需类型
推导、控制流降低或求值。估计核心实现 20–40 分钟，边界验证另需 30–60 分钟，
具体取决于原前端的结构和已有测试。

主要难点按容易失分的程度排序：

1. **不局限于变量初值。** 新 PrimaryExp 会出现在 return、参数、数组下标、
   ConstExp、条件、强转操作数、嵌套 selector 和分支值中。只增加专用赋值
   分支或遗漏 FIRST 集判断会丢失这些入口。
2. **错误恢复必须不吞 token。** case/default 缺箭头后，紧接的 switch、负号、
   标识符等应作为 Exp 的开始；缺分号后下一分支仍须继续分析。
3. **行号来自前一个终结符。** 多行标签、复杂值和嵌套 switch 的末尾不能
   简单使用当前 token 行号或 case/return 关键字行号。
4. **输出顺序要求精确。** SwitchArm 的分号须先于标签输出，SwitchExp 的
   右花括号须先于标签输出，再归约 PrimaryExp/UnaryExp 等上层成分。
5. **旧前瞻可能有隐藏假设。** 本项目原来按一行及首个分号区分赋值，新分支
   的内部也含分号，因此数组下标中的 switch 是很有区分度的测试。
6. **提交阶段隔离。** 已完成后端的同学如果继续运行语义或 IR，可能因新 AST
   未被支持，或题目根本不要求检查的语义问题而失败。

从出题角度，本题主要考察递归下降前端的扩展能力与恢复质量，算法负担较小；
综合及多行错误点可以有效区分只通过样例和完整实现。

## 题面与测试建议

题目核心文法与样例一致，可用于验题。发布前建议明确以下边界：

- `{SwitchArm}` 按文法允许零分支；未要求 default，也未限制重复标签或
  多个 default。当前仅语法分析阶段均接受，测试不应额外按语义错误判定。
- `case Number` 只允许 IntConst/CharConst，不自动扩展为负数或任意 ConstExp。
- 同一行同时缺失多个符号时，题面只规定按行号排序，未规定是否保留多条及
  同行顺序。本实现沿用项目 Reporter 的“行号、错误码排序并去重”；建议
  评测说明明确此约定，或避免用未约定的同行顺序扣分。
- `->` 是一个连续的 token，`- >` 或中间隔注释不应等价于箭头。
- 直接以 switch 开头的 Stmt 必须使用语句形式；括号或一元运算包裹的
  switch 表达式可以出现在表达式语句中。分隔符写错不是本题新增错误恢复
  的合法替代形式，不应把冒号自动当作箭头。
- 附件“如下内容的 json”之后没有实际给出对象；建议发布版本补全。
  本提交使用 `{"programmingLanguage":"Java"}`，不携带目标码设置。

建议优先加入 testcase9（数组下标）、testcase14（多重恢复）、CRLF、多行
char/default 标签和空分支用例；这些边界比扩大纯算术表达式更有辨识度。
